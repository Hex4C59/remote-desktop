## 1. 线程清单

两端线程集合相同，被控端与控制端只是各自启用不同的工作。

| 线程 | 数量 | 职责 | 明确禁止 |
| --- | --- | --- | --- |
| Capture | 1 | 从平台取帧，写入 1 帧槽 | 编码、缩放转换、网络 I/O、写盘、阻塞等待、日志字符串拼接 |
| Encode | 1 | 取帧编码，输出到发送队列 | 等待网络、等待 UI、同步写盘、动态扩容 |
| Network | 1 | socket 收发、分片重组、加密、保活 | 编码、渲染、文件 I/O、业务状态机串行化 |
| Session（串行执行器） | 1 | 会话状态、授权门禁、超时、代次 | 采集、编解码、写盘、等待阻塞操作 |
| Input（串行执行器） | 1 | 输入队列消费、按压状态记账、注入调度 | 等待下一帧、等待网络、写盘 |
| Decode（控制端） | 1 | 解码、产出可渲染帧 | 阻塞 UI 线程、持有 UI 资源 |
| UI（控制端） | 1 | 窗口、渲染、输入事件采集 | 网络读取、解码、磁盘 I/O |
| Writer（可选） | 1 | 统计/证据异步写盘 | 参与任何热路径判定 |

约束：

- 线程数固定，**不按会话或按设备创建线程**；新会话复用同一组线程。
- 除上述之外不得新增线程或线程池。确实需要时先改本文、写进规格并取得批准。
- 每个线程有名字，便于抓取线程栈与延迟归因；线程创建与销毁集中在一处。
- 线程归属写在文件头注释里，格式固定为 `// Thread: <线程名>`，
  取值必须是上表的线程名或 `any` / `none`。新增取值等于新增线程，须先改本文。

判定新线程：在 `src/` 里搜索 `std::thread`、`std::jthread`、`pthread_create`、
线程池类的构造点。出现不在白名单文件中即为违规。

## 2. 交接边沿

每一节描述一条**允许的**跨线程数据流。不在这张清单里的跨线程通信一律视为违规。
[§2.9](#29-m1-会话交接)补充 M1 允许的会话交接。

```text
Capture ──①帧槽──► Encode ──②发送队列──► Network
Network ──③接收帧队列──► Decode ──④最新帧──► UI
Network ──⑤控制消息──► Session
Session ──⑥授权门禁──► Input
Input ──⑦平台注入──► platform
任意线程 ──⑧事件队列──► Writer
```

### 2.1 ① Capture → Encode（帧槽）

| 项 | 规则 |
| --- | --- |
| 移交内容 | 帧引用（所有权或共享引用），不是拷贝，不是像素数据复制 |
| 容量 | 1 帧。**不得大于 1**，加容量等于加延迟 |
| 满时行为 | Capture 覆盖旧帧并释放它；**绝不等待、绝不重试、绝不返回错误让上层重试** |
| 反向流 | 无。Encode 不得向 Capture 发送任何东西，包括“我忙”“稍等” |
| 详细契约 | [屏幕帧移交](../increments/002-screen-frame-handoff/spec.md) |

**违反长什么样**（任一条即为违规）：

- `publish()` 内部出现 `lock`、`wait`、`sleep`、条件变量、`malloc`/`new`。
- 队列容量是 2 或更多，或写成 `std::deque<Frame>` 之类的可增长容器。
- Capture 循环里出现“等编码器取走”的计数等待或超时重试。
- Encode 侧通过回调/引用反向调用 Capture 的任何方法。

### 2.2 ② Encode → Network（发送队列）

| 项 | 规则 |
| --- | --- |
| 移交内容 | 已完成编码的帧（或其分片描述），带帧类型与时间戳 |
| 容量 | 按**时间**预算，默认 ≤ 2 帧等价字节；不得用“帧数”表示，因为帧大小可变 |
| 满时行为 | 丢弃最旧的非参考帧；只有整组可丢（GOP 边界）才允许丢，必要时强制关键帧重建 |
| 反向流 | 无。Network 不得因拥塞向 Encode 同步回压（例如 `wait_for_space()`） |
| 反压方式 | 只允许**异步信号**：Network 更新一个原子拥塞标记，Encode 在下一帧开始前读取它调整码率/帧率 |

**违反长什么样**：

- Encode 线程里出现 `send()`、`recv()`、socket 或 TLS 调用。
- Network 线程阻塞在“等 Encode 出帧”（条件变量、信号量、future）。
- 队列用“最多 N 帧”而不是字节/时间预算，导致大关键帧时内存爆掉。
- 丢帧时丢了参考帧却没强制关键帧 → 解码端持续花屏。

### 2.3 ③ Network → Decode（接收帧队列）

| 项 | 规则 |
| --- | --- |
| 移交内容 | 已重组完整的帧数据（或引用），带帧类型与到达时间 |
| 容量 | 单帧分片上限 + 同时在途帧数上限，二者都是常量 |
| 缺片时 | 不等待补齐；丢弃该帧并请求关键帧 |
| 反向流 | 无。Decode 不向 Network 发送任何同步请求 |

**违反长什么样**：

- Network 线程里出现解码、色彩转换、纹理解码。
- 为等待缺失分片而保留帧直到超时（会让延迟随丢包累积）。
- `wait_for_frame()` 之类会阻塞 Network 的接口。

### 2.4 ④ Decode → UI（最新帧）

| 项 | 规则 |
| --- | --- |
| 移交内容 | 可渲染帧（位图或纹理句柄），所有权明确 |
| 容量 | 1–2 帧，**覆盖式**：新帧到达时旧未渲染帧被丢弃 |
| 满时行为 | 覆盖旧的，不排队。UI 慢就是丢帧，不是堆积 |
| 反向流 | 无。UI 不得阻塞 Decode 等垂直同步 |

**违反长什么样**：

- 渲染队列是无界 `std::vector` 或 `std::queue`。
- UI 线程里直接读 socket、解码或做磁盘 I/O。
- 用“主线程投递 + 同步等待结果”的跨线程调用。

### 2.5 ⑤ Network → Session（控制消息）

| 项 | 规则 |
| --- | --- |
| 移交内容 | 已解析的控制消息事件（不可变，按值或 `shared_ptr<const T>` 传递） |
| 容量 | 256 条，`bye`/`error` 有单独预留。M1 的 `input.pause` 用 §2.9 的独立槽 |
| 满时行为 | 丢弃普通消息并计数。有效 `input.pause` 必须保留，无法保留则走独立关断槽 |
| 反向流 | Session 可向 Network 投递发送请求，但**不得同步等待发送完成** |

**违反长什么样**：

- Session 执行器里出现 socket 读写、JSON 解析大循环或阻塞队列弹出。
- Network 线程直接改 Session 状态字段（而不是投递事件）。
- Session 里 `future.get()` / `wait()` 等待 Network 返回。

### 2.6 ⑥ Session → Input（授权门禁）

| 项 | 规则 |
| --- | --- |
| 移交内容 | 绑定本地会话代次的原子门禁，包含 `input_epoch`、授权、代次是否封闭及会话是否终止封闭 |
| 一致性 | Session 独占开启权。封闭与 Input 单次许可申请在同一原子状态排序，终止封闭后同一会话禁止重开 |
| 反向流 | Input 注入失败时终止封闭门禁，经独立槽上报。Session 独占会话状态迁移 |
| 关断顺序 | 进入 `Ending` 时**先关输入门禁**再停采集，见架构总览 5.3 |

**违反长什么样**：

- Input 线程自己判断“会话是否还在”，而不是读 Session 给出的门禁。
- 关断时先停采集再关输入门禁（会让已按下的键留在系统里）。
- `input_epoch` 在 Input 线程本地自增，而不是由 Session 分配。

### 2.7 ⑦ Input → platform（注入调用）

| 项 | 规则 |
| --- | --- |
| 移交内容 | `InputEvent`（含时间戳、`input_epoch`、显示映射版本） |
| 阻塞 | 注入调用不得等待渲染、网络或下一帧。普通注入返回错误时，Input 在申请下一条许可前封闭门禁并请求关断 |
| 记账 | 按平台确认的效果记账，保留可能仍按下的项。清理以 `release_all_pressed()` 确认全部释放为准 |
| 输入注入的调用约定 | [platform-abstraction.md](platform-abstraction.md) 第 4 节 |

### 2.8 ⑧ 任意线程 → Writer（事件队列）

| 项 | 规则 |
| --- | --- |
| 移交内容 | 定长的统计事件（POD 或定长字符串），**不在入队时拼接字符串** |
| 容量 | 4096 条；溢出即丢弃并置“证据不完整”标记 |
| 满时行为 | 绝不阻塞调用方；写盘失败不重试到热路径 |
| 回执 | 只有真正写盘成功后才回执，不能先回执再异步补写 |

**违反长什么样**：

- 热路径里出现 `std::string` 拼接、`printf`、`std::format`、`ofstream <<`。
- 队列满时 Writer 让采集线程阻塞（例如有界阻塞队列）。
- 统计写入与“画面已显示”混为同一回执。

### 2.9 M1 会话交接

下列交接由已获批的 [001 接口约定](../increments/001-android-controls-windows-over-lan/spec.md#2-接口约定) 定义。
两端沿用第 1 节的线程数量。被控端 UI 负责本机配对、授权提示和撤权。启用配对持久化的端点使用 Writer 完成信任文件 I/O。

| 交接 | 数据及上限 | 满时或关断行为 |
| --- | --- | --- |
| 控制端 UI → Network | 键鼠事件，合计 32 条且本端排队不超过 500 ms，指针移动可覆盖旧移动 | 超限通过独立的关断信号结束会话，不跳过可靠键鼠事件继续执行 |
| 被控端 Network → Input | 已认证且通过格式检查的事件，合计 32 条且本端排队不超过 500 ms | 超限结束会话，门禁关闭指令不占用此队列 |
| Session → UI | 配对与授权提示、当前会话和输入状态，每类一个最新状态槽 | 新状态覆盖旧状态。UI 提交决定时必须带原提示的 ID |
| UI → Session | 配对和授权决定、焦点状态、Windows 首帧渲染确认及本机结束，各用一个会话或配对作用域槽 | 首帧通知带当前协商代次。迟到决定不作用于新提示。暂停、结束信号独立于普通事件队列 |
| Session → Capture / Encode / Network / Decode / UI / Input，及各线程回 Session | 每个线程一个带会话代次的生命周期命令槽和一个完成确认槽 | 同代次关闭优先且保持可见，普通流量不能覆盖。Session 异步收集退出确认，全部完成才复用 |
| Capture → Encode | 复用 ①，关闭时用 Capture 停止发布确认触发 Encode 消费并释放剩余帧 | Encode 确认所有本会话帧已释放前不得开启下一次采集，帧池和帧槽继续存活 |
| Network → Session | 一个独立 `input.pause` 接收槽，带已校验的连接、会话、代次与接收顺序 | 普通队列满时仍可交付。匹配当前代次的有效暂停无法入槽时，经独立关断槽结束会话 |
| Input / Network / UI → Session | 每来源一个带会话代次和原因的关断请求槽 | 同代次重复信号可合并，普通输入和控制消息不能覆盖。Input 注入失败时先封闭门禁再投递 |
| 被控端桌面观察回调 → 门禁及 Session | [005 桌面状态](../increments/005-windows-desktop-state/spec.md) 定义订阅代次和观察序号。一个关断请求槽和一个最新桌面状态槽 | 不可交互通知先封闭再投递。快照和恢复只可更新同代次的最新状态。关断请求保持可见，旧会话回调无效 |
| Session → Network | 在 ⑤ 的反向通路上发送控制消息，普通发送请求最多 256 条，复用生命周期停止信号 | `input.pause`、`input.suspended` 等协议交互无法发送时经独立关断槽结束当前会话。停止不依赖 `bye` 送达 |
| Capture → Session | 当前会话初始显示映射一个结果槽，映射变化使用该来源的关断请求槽 | 初始映射用于 `media.offer`。检测到变化时 Capture 停止发布新帧，Session 处理关断请求后关闭门禁。旧会话通知不推进新会话状态 |
| Session ↔ Writer | 每端最多一项在途配对写入，以及一个结果槽 | Session 串行裁决取消与最终提交许可，Writer 报告带尝试 ID 的原子写入结果。取消先于许可时清除暂存，许可先于取消且写入成功时保留本端记录。迟到结果不推进已终止的流程 |

Network 按认证控制通道的接收顺序检查 `input.pause` 的连接、会话、消息方向、序号和负载，
通过 Session 发布的当前代次状态筛除不适用的暂停。Session 按同一连接的接收顺序归并普通信令与暂停槽，
消费时复核状态。槽中同一会话及代次的有效重复暂停可合并，保持首个暂停的接收位置。
无法保留有效暂停时向独立关断槽投递，Session 关断前复核其连接、会话及代次。

被控端 Session 与 Input 共享第 ⑥ 条边沿的原子门禁状态。平台桌面回调和 Input 仅能终止封闭其所属的会话门禁。
桌面回调同时使用独立的状态槽报告桌面恢复。已获许可的单次平台调用可完成，Input 先记账再清理。
注入失败时同一 Input 执行器在接收下一条输入前封闭门禁，清空待执行输入并投递关断信号。
清理和生命周期确认使用独立的状态槽，Session 无需同步等待。
Session 依据超时和确认状态报告关断。端点退出才销毁工作线程，具体顺序见 [001 §7](../increments/001-android-controls-windows-over-lan/spec.md#7-线程与资源)。

### 2.10 Android 控制端线程映射（待评审）

[007](../increments/007-android-controller/spec.md) 将 UI 映射到 Android 主线程。Decode 管理解码器、输出索引和呈现提交。Network 管理收发和认证上下文，Session 串行维护会话，Writer 异步写入。应用执行器跨会话复用。

| 交接 | 上限与关断行为 |
| --- | --- |
| UI → Decode | 一个带会话、协商和表面代次的 Surface 更新槽。失效走独立停止路径。Decode 异步归还输出索引及 Surface 引用 |
| Decode → Session | 一个首帧回执槽，只接纳匹配当前表面代次的系统呈现回调。Session 复核代次后发送 `session.ready` |
| UI → Session / Network | 复用 §2.9 的焦点、关断与输入交接。焦点丢失、手势取消或当前矩形失效时立即停采集并作废待发输入。退后台或当前 Surface 销毁时结束会话 |

Android 的 Decode 按系统编解码器约定向 Surface 输出，应用层最多保留一个待提交输出。UI 不等待 Decode、Network 或 Session。Windows 的最新帧交接仍见 §2.4。

## 3. 队列与缓冲总表

| 队列 | 上限 | 溢出策略 | 理由 |
| --- | --- | --- | --- |
| 采集帧槽 | 1 帧 | 新帧覆盖未处理旧帧 | 旧画面无价值，排队只会增加延迟 |
| 编码发送队列 | 按时间预算（默认 ≤ 2 帧等价字节） | 丢弃最旧的非参考帧，必要时强制关键帧 | 保新不保全 |
| 接收重组缓冲 | 单帧分片上限 + 帧数上限 | 丢帧并请求关键帧 | 不允许为缺片无限等待 |
| 解码待渲染 | 1–2 帧 | 覆盖旧的未渲染帧 | 渲染滞后必须被吸收而不是堆积 |
| 控制消息队列 | 普通 256 条，`input.pause` 单独 1 槽 | 普通队列满不影响暂停入槽。有效暂停无法保留时经独立关断槽结束会话 | 保证失焦暂停在普通信令积压时可观测 |
| 输入队列 | 每端 32 条、排队 ≤ 500 ms | 超限结束会话并释放按压 | 丢部分文字后继续执行 Enter 更危险 |
| 统计事件队列 | 4096 条 | 丢弃并标记证据不完整 | 证据完整性优先于补写 |
| 写盘批次 | 按时间或条数 | 溢出即失败上报，不阻塞调用方 | 慢盘不能拖住热路径 |

附加规则：

- 所有队列容量都是编译期或配置期常量，**不在热路径扩容**。
- 队列深度、入队失败、丢弃计数必须可观测，并进入统计。
- 有依赖关系的已编码帧不能任意丢弃；只允许在参考帧边界丢整组。
- 队列时间用各端本地单调时钟测量，不相减两端时间戳。

## 4. 延迟预算

### 4.1 目标

| 场景 | 端到端目标 | 判定口径 |
| --- | --- | --- |
| 局域网直连 | 操作反馈 P95 < 50 ms | 性能目标。M1 验收要求每类操作 P95 ≤ 200 ms，见架构总览 8.3 |
| 广域网（M3） | 操作反馈 P95 < 150 ms | 性能目标，网络条件由 M3 规格定义 |
| 单帧捕获周期 | ≤ 33 ms（30 FPS） | 采集触发到入队完成 |

这些数值是设计目标。Windows 本地采集按 003 的真机口径验证，端到端目标按 001 验收。 [Windows 真机验收](../increments/003-platform-win/spec.md#52-真机testsintegration需交互式桌面)

### 4.2 阶段预算（局域网，待测量验证）

| 阶段 | 预算 | 超限时的动作 |
| --- | --- | --- |
| 采集（含格式描述） | ≤ 6 ms | 降低采集频率，记录降级原因 |
| 编码 | ≤ 12 ms | 降码率/帧率，切换编码器前必须单独验证 |
| 传输（单程 + 排队） | ≤ 10 ms | 检查发送队列深度，是否是队列而非网络 |
| 解码 | ≤ 8 ms | 降低分辨率，记录解码耗时分布 |
| 渲染提交 | ≤ 4 ms | 检查是否在 UI 线程做了别的事 |

Windows Capture 独占 staging 纹理和完成查询。GPU 读回忙时返回 `kTimeout`，由 Capture 的下一次取帧调用轮询。单笔读回从原采集时间戳开始计龄，达到 33 ms 仍未开始 CPU 拷贝就作废。PWH-06 对每次零等待调用应用 6 ms 预算，包含提交、轮询和无帧返回，并记录交付帧龄。 [Windows 读回约定](../increments/003-platform-win/spec.md#41-提交桌面帧拷贝与读取像素)

预算分配不满足时，先核对测量范围、交付帧率和帧龄，再评审架构。缓冲区内的停留时间计入帧龄，超限仍按原预算判定。

### 4.3 不进热路径的东西

以下操作禁止出现在 Capture / Encode / Network / Decode / UI 的关键路径上：

- 同步文件 I/O 与 `flush()`；格式字符串拼接与日志输出；堆分配的动态扩容；
- 锁竞争（尤其是跨线程共享互斥量）；异常作为控制流；字符串解析（JSON 解析不得在每帧发生）；
- 等待其他线程的返回值。

**判定方法**：对每个热路径函数，问三个问题——
(1) 有没有可能阻塞在别的线程上？(2) 有没有可能申请内存？(3) 有没有可能碰磁盘？
任一为“可能且没有硬上限”，就是违规。

提交前逐条对照。任何一条答“否”都要说明原因，不能默认通过。

## 6. 可测性要求

- 每个线程的关键阶段必须能打点（单调时钟，纳秒或微秒），打点本身不得分配内存。
- 统计格式一旦确定即视为契约；改字段须同步对应增量规格与工具。
- 单元测试用 mock 平台接口，不依赖真实屏幕或真实网络；集成测试用真实线程，但不依赖真实显示器。
- 任何声称“优化了延迟”的变更必须附上前后对比数据、测量条件与版本；没有数据不进热路径。

## 7. 变更流程

改动本文任何一条之前：

1. 在 `docs/increments/` 下新增或更新对应规格，写清不变量与验收场景；
2. 更新本文件；
3. 再改代码。

反过来做（先改代码再补文档）视为违规，须回退。
