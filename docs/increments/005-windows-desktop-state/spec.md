# Windows 桌面状态观察与输入关断

status: approved
approved-by: Hex4C59, 2026-11-24

## 1. 范围

为 [001 M1](../001-android-controls-windows-over-lan/spec.md) 的 Windows 被控端提供本机桌面初始状态、带会话代次的变化通知及输入门禁关断契约。覆盖当前进程关联的交互会话。Session 0、无交互桌面和无法证实当前桌面状态的环境均不能开启门禁。普通输入及按压释放由 [003](../003-platform-win/spec.md) 定义。

## 2. 接口约定

公共接口、类型、方法错误及线程见[平台抽象 §5](../../architecture/platform-abstraction.md#5-会话与桌面状态)，其为声明的唯一定义处。`SessionState` 是平台观察器，`001` §2.1 的同名枚举是会话控制状态，两者分属不同模块。平台观察器报告桌面事实，Session 独占业务迁移及门禁开启权。

### 2.1 初始快照与通知

1. Session 预先安装代次 `g` 的关闭门禁和空槽，再调用 `subscribe(g, callback, context)`。平台必须在同一状态序列上登记订阅并读取初始快照。快照序号为 `s`，该订阅后续报告的变化序号严格大于 `s`。回调可以在 `subscribe` 返回前发生。Session 采用当前代次的最高序号作为最新桌面状态，初始快照不能回写更旧状态或清除终止标记。
2. 快照为非 `kInteractive` 时终止封闭 `g`。即便较新通知已恢复交互，初始不可交互仍使此次授权尝试失败。订阅失败同样关闭此次尝试，不留下有效订阅。两种路径均报 `kSessionNotInteractive`，待决时作废授权，已批准时进入 `kEnding`。
3. 每条通知按值携带订阅时的 `g` 与观察序号，序号只在同一订阅内比较。平台对同一订阅串行发布通知，状态经确认才可报告为 `kInteractive`。失去可信状态时发布 `kUnknown`。重复状态可以合并，已观察到的任一不可交互转换必须交付给回调，即使随后恢复。
4. Session 在会话任务退出且按压清理确认后撤销订阅。撤销使此后未开始派发的回调失效，先前已开始派发的回调可以晚到。回调携带原代次，门禁及两个槽均以代次为写入条件。旧代次无法封闭新会话或覆盖当前槽。端点保留回调上下文，直到平台事件源停止且已开始派发的回调全部退出，再由所有者释放。

### 2.2 门禁与清理

- 当前代次的非 `kInteractive` 回调先在与单次注入许可共用的原子状态上设置终止封闭，再写独立关断槽及最新状态槽。普通队列是否满、Session 是否调度均不影响封闭。关断槽中同代次重复请求合并，恢复通知只可更新最新状态槽。
- 封闭先于许可时平台普通调用为零次。许可先于封闭时可完成该次调用并按实际效果记账，之后不再取得许可。提交门禁开启也在同一原子状态上校验代次、桌面可用性和终止标记。
- Session 消费关断后作废待决授权，或结束已批准会话并停止采集。由 Input 执行器走本地释放路径。`kInteractive` 仅可触发待清理项重试。需保留观察直至按压清理确认，以接收恢复通知。新会话在资源退出与清理确认后使用新代次重新授权。

## 3. 不变量

- 只有可信的 `kInteractive` 快照或状态可作为开启门禁的桌面前置条件，仍须满足 001 的授权和输入握手条件。
- 终止封闭对本地会话代次单调，最新桌面状态对该代次的序号单调。恢复无法复活旧会话。
- 平台回调只做代次检查、原子封闭及有界投递。Session 消费关断和清理结果，Input 记账并释放。

## 4. 线程与资源

| 对象 | 所有者与上限 |
| --- | --- |
| 平台观察器与订阅 | Session 安装、撤销，每端一个有效订阅。平台事件源在既有线程或系统回调分发通知，同一订阅串行发布 |
| 门禁与回调上下文 | 端点持有，生命周期覆盖底层事件源摘除及在途派发退出。Session 开启，回调只允许终止封闭，Input 申请单次许可 |
| 关断槽与最新桌面状态槽 | 各一槽，独立于普通信令。关断同代次合并并保持可见。状态槽仅接收匹配代次且较新的状态 |

Session 不同步等待回调退出或按压释放。观察器无法持续提供可信状态时按 `kUnknown` 路径处理。关断与寿命交接沿用 [线程模型 §2.9](../../architecture/threading.md#29-m1-会话交接)。

## 5. 验收场景

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| DS-01 | 订阅成功，初始交互，随后锁屏 | 快照和通知带原代次，锁屏序号大于快照 |
| DS-02 | 安装失败，或成功但初始状态为未知、锁屏、安全桌面或注销 | 开启被拒绝并报告 `kSessionNotInteractive`。订阅失败无有效回调，初始不可交互的代次即使恢复也不可开启 |
| DS-03 | 分别在 `subscribe` 返回较旧的交互快照前发布锁屏，以及在返回较旧的锁屏快照前发布恢复 | 两种顺序均保持该代次终止封闭，最新状态取较高序号 |
| DS-04 | 普通信令队列满且 Session 暂不消费，分别安排锁屏或未知的封闭先于和后于单次许可 | 许可调用分别为零次和至多一次，已许可调用仍记账。独立关断槽可见 |
| DS-05 | 关断尚未消费时恢复交互 | 关断槽保持可见，最新状态供待清理项重试，原代次仍关闭 |
| DS-06 | 撤销后启动新代次，再交付旧代次已开始派发的锁屏和恢复通知 | 新门禁、关断槽和最新状态槽不变。端点销毁前等待平台分发退出的确认，Session 保持可调度 |
| DSH-01 | Windows 交互式桌面上记录锁屏、解锁、注销和可取得的安全桌面转换 | 保存状态序列、代次、封闭及清理重试证据。证据说明识别为 `kUnknown` 的情形 |

`DS-01`–`DS-03`、`DS-06` 的观察器部分使用 mock 状态源。`DS-04`–`DS-06` 的完整门禁行为关联 `M1U-30`，由 M1 波次 3 验证。

## 6. 依赖与待决项

仅使用 Windows SDK 与仓库现有测试框架。方案需通过真机证明选用的状态来源可以覆盖 `DSH-01`，覆盖不到的状态按 `kUnknown` 处理。 `003` 的采集和注入只使用已确认的桌面状态分类，平台调用的通用失败不能单独证明安全桌面。

## 7. 并发自检

| 编号 | 约束 |
| --- | --- |
| T-01、T-02 | Session 管理订阅，平台回调使用 §2.9 桌面观察边沿，共用 ⑥ 门禁 |
| T-03 | 关断与最新状态各一槽，当前代次写入，恢复只覆盖状态槽 |
| T-04、T-05 | 回调无锁、无分配、无同步 I/O，Session 异步接收清理和退出确认 |
| T-06 | 先关门禁，再停会话任务，释放确认后才复用 |
| T-07、T-08 | 实现标明文件线程归属，沿用既有线程及平台事件源 |
| T-09 | 关断生效点用同步点验证，延迟证据纳入 M1 验收 |
