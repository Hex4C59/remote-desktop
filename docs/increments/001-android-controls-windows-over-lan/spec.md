## 1. 范围

M1 在同一局域网内交付 **Android 控制端 + Windows 被控端**。先验证配对、本机授权和实时画面，再验证触控、键盘与可测量的操作反馈。

包含：

- Windows 被控端运行在已登录、未锁屏的交互会话。
- Android 控制端在前台运行，按 [007 Android 控制端](../007-android-controller/spec.md) 定义画面、触控及键盘能力。
- 双方在同一局域网，直连，无控制面服务器、无中继。
- 现场配对一次登记设备身份。每次远控仍须被控端本机用户批准本次权限。
- 单显示器、单视频轨道、单活动控制端。
- 采集 → 编码 → 传输 → 解码 → 渲染，以及输入反向链路。

不包含：

- 公网、NAT 穿透、TURN、中继、无人值守授权。
- 文件传输、音频、剪贴板、多显示器、自适应画质、会话内显示映射切换及重新协商。
- macOS/Linux 被控端与被控平台支持声明。
- Windows 原生控制端按 [006](../006-windows-render-surface/spec.md) 后续推进。Android 被控端采集按 [004](../004-android-screen-capture/spec.md) 独立验收。

## 2. 接口约定

### 2.1 会话状态

```cpp
enum class SessionState {
  kIdle, kRequesting, kAuthorizing, kNegotiating, kStreaming,
  kRejected, kEnding, kFailed
};

struct SessionLimits {         // 来自平台与会话配置
  uint32_t max_width, max_height, max_fps;
  uint32_t max_bitrate_bps;
  std::chrono::milliseconds input_queue_deadline;   // 默认 500 ms
  uint32_t input_queue_depth;                       // 默认 32
};
```

状态迁移与不变量见 [架构总览](../../architecture/overview.md) 6.2。
所有迁移由 Session 串行执行器完成。跨线程可按 §2.3 封闭输入门禁，并投递带会话代次的事件。会话槽位在进入 `kAuthorizing`
前保留。被控端 Session 串行化本机批准与待决请求取消。批准前拒绝或超时走 `kRejected → kIdle`，
作废待决授权并释放预留槽位。批准是建立会话的分界点。此后媒体拒绝、断线或 30 秒内未确认首帧
都进入 `kEnding`，并在工作退出与按压清理确认后释放槽位。`kFailed` 可进入清理，但清理未确认时
禁止回到 `kIdle`。

### 2.2 配对、认证与授权

- 配对在被控端本机开启的配对窗口内进行。配对通道通过标准密码认证密钥交换（PAKE）建立，
  两端在同一次受保护交互内绑定长期身份并现场核对短码。被控端本机确认后发送 `pair.confirm`，
  双端写入顺序与异常恢复以[控制协议 §3](../../protocol/README.md#3-首次配对)为准。
  两端的 Session 各自串行裁决取消与最终提交许可，Writer 异步写入并按尝试 ID 回报实际结果。
  取消先于许可时清除暂存。许可先于取消且写入成功时保留本端记录。被控端只报告本端已登记，
  控制端在收到 `pair.complete` 且本地激活成功后才报告配对成功。中断后同一身份可重新现场确认，
  幂等补齐双方记录。配对结束后关闭临时通道。远控仍须另建认证连接并取得本机授权。
- 每次会话使用新密钥建立双向认证的传输通道。两端必须验证对端持有其信任记录对应的长期私钥。
  质询、会话请求、实际授权、媒体、输入和保活都属于同一认证连接。媒体和输入分通道的记录须受
  同一认证上下文保护，并绑定会话标识及通道。认证失败、关系不匹配或通道失效时拒绝交付媒体和输入。
- 会话质询只在认证完成后发出，仅对当前连接有效且只能消费一次。被控端本机显示已认证设备和
  请求权限。用户在 60 秒内显式批准的权限才随 `session.accept` 发出。拒绝、超时、桌面不再可交互
  或连接关闭后作废待决授权。`view` 必须获授，`mouse` 和 `keyboard` 独立授予。
  M1 的本机撤权结束会话，重新连接须重新批准。

### 2.3 输入门禁与清理

- 被控端 Session 在确认首帧后为已获准输入的会话发布 `input.prepare`，包含新 `input_epoch`。
  控制端清空待发输入后回 `input.ready`。被控端门禁生效后回 `input.enabled`，此时控制端才可发输入。
  仅查看会话直接维持关闭门禁。暂停时封闭当前代次，清空输入队列并清理按压。恢复必须等待清理确认、
  交互桌面与授权仍有效，再用新代次执行同一握手。收到当前会话、当前已准备或已开启代次的有效 `input.pause` 时，
  Network 将其交给独立暂停槽，Session 按控制消息接收顺序处理。普通收队列满时仍须处理暂停并回 `input.suspended`。
  有效暂停无法保留，或 `input.pause`、`input.suspended` 无法入发送队列时，经独立关断槽结束会话。
  旧会话、旧代次及未通过协议校验的消息不得触发此路径。
- 每次普通注入由 Input 申请单次许可。门禁状态绑定本地会话代次和 `input_epoch`，许可同时校验会话、代次、授权、
  桌面可用性和队列时限。Session 独占开启权，开启必须核对当前代次未封闭且本会话没有终止封闭标记。
  所有封闭操作与许可申请在同一原子状态上排序。封闭操作生效后不再授予相应许可。已取得许可的单次平台调用可以完成，
  Input 先记账其实际效果，再清理。未取得许可的输入不得保留到恢复后执行。
- Session 按 [005 的接口约定](../005-windows-desktop-state/spec.md#2-接口约定) 安装桌面状态订阅并取得同一序列中的初始快照。
  订阅失败或初始状态不可交互时终止封闭门禁。当前会话的非 `kInteractive` 通知（含 `kUnknown`）
  由回调先在同一原子状态上终止封闭门禁，再经独立关断槽通知 Session。封闭自该原子操作生效，Session 异步消费。
  初始快照不能覆盖更高序号状态或清除终止封闭。迟到的旧会话回调无效。
  后续交互桌面恢复通知只能允许本地清理重试，原会话保持终止封闭。
- `InputInjector::inject` 返回错误时，Input 须在领取下一条输入前终止封闭门禁，保留已确认或可能仍按下的记录，
  清空待执行输入，并经独立关断槽要求 Session 进入 `kEnding`。平台明确报告桌面不可用时使用 `kSessionNotInteractive`，
  其他普通注入失败使用 `kInputInjectionFailed`。不补发失败事件或队列中的后续输入。
- 关断清理由 Input 执行器执行，属于独立的本地释放路径，只释放本程序记账的按压。
  清理完成以平台确认全部释放为准。部分成功保留未释放项，无法确认的项视为仍待清理。
  桌面不可用时保持门禁关闭并等待恢复通知。清理确认超过 500 ms 时报告 `kInputCleanupPending`，
  不阻塞 Session。暂停期间清理失败或超时则转入会话关断。桌面恢复时重试，其他失败允许由本机用户触发重试。
  清理未确认期间保持不可复用，同时终止旧会话的采集、推流与传输。清理确认及其他资源退出后才释放会话槽位。
- Capture 取得初始显示映射并向 Session 报告。Session 固定本次会话的 `display_map_version`，
  由 `media.offer` 传给控制端。普通鼠标输入须携带该版本，Input 在申请许可前丢弃并计数版本不符的事件。
  Capture 检测到显示映射变化时停止发布帧，经带会话代次的关断请求通知 Session。Session 处理请求时
  关闭门禁并进入 `kEnding`。Input 按本地释放路径清理已记账的按压，释放不需要旧坐标。
  清理和退出均确认后，用户可重新连接并取得本机授权，新会话使用届时的显示映射。

### 2.4 错误码

| 错误 | 触发 | 处理 |
| --- | --- | --- |
| `kNotPaired` | 对端身份没有匹配的已提交信任记录 | 认证失败，提示现场配对，不发会话质询 |
| `kAuthenticationFailed` | 对端未证明信任记录对应的身份，或连接绑定检查失败 | 关闭连接，不开放媒体与输入 |
| `kBadPassword` | 配对认证库确认口令验证失败 | 计数 +1，达 3 次作废配对窗口 |
| `kCodeMismatch` | 现场用户报告短码不一致 | 终止本次配对，清除本次暂存记录 |
| `kPairingNotSaved` | 本次配对写入或激活失败 | 中止配对并显示失败，按协议恢复部分写入 |
| `kUserDenied` / `kAuthorizationTimeout` | 本机用户拒绝 / 60 秒未确认 | 回 `session.reject`，释放待决授权槽位 |
| `kBusy` | 已有活动、待批准或清理未确认的会话 | 拒绝，不影响当前会话 |
| `kUnsupportedCodec` | 控制端不接受 `media.offer` | 进入 `kEnding`，`bye.reason=error` |
| `kFirstFrameTimeout` | 本机批准后 30 秒内未收到有效 `session.ready` | 进入 `kEnding`，`bye.reason=error` |
| `kDisplayChanged` | 当前会话的显示映射变化 | 进入 `kEnding`，关门禁并清理按压，`bye.reason=error` |
| `kSessionNotInteractive` | 锁屏、注销、安全桌面、桌面状态未知或无法订阅 | 禁止开启门禁。待决授权失效，已批准会话关闭门禁并清理按压 |
| `kControlQueueOverflow` | 有效 `input.pause` 无法进入接收保留槽，或 `input.pause`、`input.suspended` 无法进入发送队列 | 经独立关断槽结束会话，普通控制队列无需先腾空 |
| `kInputInjectionFailed` | 普通注入调用失败，非 `kSessionNotInteractive` | Input 先封闭门禁，保留实际及未确认的按压效果，Session 进入 `kEnding`，`bye.reason=error` |
| `kInputQueueOverflow` / `kInputQueueExpired` | 输入队列超深度 / 超本地排队时限 | 结束会话，关门禁，清理按压 |
| `kInputCleanupPending` | 平台拒绝释放、效果不确定或清理确认超时 | 保留未确认项并显式上报，禁止恢复输入和复用槽位 |
| `kTransportClosed` | 传输层断开或保活超时 | 结束会话，关门禁，清理按压 |

### 2.5 线程归属

Windows 被控端启用 Capture、Encode、Network、Session、Input、UI 和 Writer 所需职责。Android 控制端
将 UI 映射到主线程，Decode 管理解码和输出，Network 管理收发，Session 管理会话迁移，Writer 负责持久化。
会话复用工作执行器，Android 限额及表面回执见 007，[线程模型 §2.9](../../architecture/threading.md#29-m1-会话交接) 记录共用交接。

## 3. 不变量

1. **Capture 线程绝不阻塞在编码器上**：采集帧槽只有 1 帧，新帧覆盖未处理旧帧。
2. **输入独立于媒体。** Input 执行器不等待编码、渲染或写盘。普通注入失败后终止会话，已确认或仍可能存在的按压按实际效果记账。
3. **授权门禁先于普通注入。** 仅 `kStreaming`、桌面可交互、当前代次已启用且事件所需权限仍有效时发放注入许可。
   桌面回调的原子封闭先于关断事件投递，封闭后的许可申请一律失败。
4. **未确认释放时保持关闭。** 进入 `kEnding`、`kFailed`、断线或锁屏时，关闭门禁并调用本地清理。
   释放动作独立于远程输入队列容量。全部按压确认释放前禁止恢复输入和复用会话槽位。
5. **会话独占**：同一被控端同一时刻只有一个活动会话；`kAuthorizing` 期间也拒绝第二端。
6. **旧消息无效**：结束的会话的 `session`、旧 `negotiation`、旧 `seq`、旧 `input_epoch`
   消息一律丢弃，不得影响当前会话。
7. **队列有界**：热路径队列上限与溢出策略固定。有效 `input.pause` 不占普通信令队列容量，无法交付时关闭会话。溢出进入统计。
8. **无敏感信息入日志**：配对口令、会话密钥、屏幕内容、按键内容不进日志与 Git。
9. **会话内显示映射固定**：映射变化后停止发布新帧，Session 处理关断请求并关闭门禁后，旧映射不再获得普通注入许可。

## 4. 验收场景

每条都须先有失败测试（[AGENTS.md §5](../../../AGENTS.md)）。测试用 mock 平台接口，
不依赖真实设备；真机验收单列。

### 4.1 单元/集成（可自动化）

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| M1U-01 | 未配对端尝试建立远控连接 | `kNotPaired`，不发 `session.challenge`，不占会话槽位 |
| M1U-02 | 配对口令错误 3 次 | 第 3 次后窗口作废，后续配对须重新在本机开启窗口 |
| M1U-03 | 短校验码不一致 | 返回 `kCodeMismatch`，双方均无本次活动信任 |
| M1U-04 | 重放已结束的配对消息 | 不接受旧连接身份或确认，不产生新的信任记录 |
| M1U-05 | 会话中第二控制端请求 | `kBusy`，原会话不受影响 |
| M1U-06 | 本机批准后媒体协商拒绝、断线或 30 秒内未确认首帧 | 进入 `kEnding` 且不进入 `kStreaming`。延迟工作退出确认时第二端收到 `kBusy`，确认后第二端可申请授权 |
| M1U-07 | 本机门禁生效前收到输入 | 丢弃并计数，无普通注入平台调用 |
| M1U-08 | 输入队列超 32 条 | 结束会话，统计记 `kInputQueueOverflow` |
| M1U-09 | 输入从本端入队起排队超 500 ms | 结束会话，统计记 `kInputQueueExpired`，旧事件不补发 |
| M1U-10 | 会话中切换锁屏 | 立即关闭门禁并进入 `kEnding`，清理受阻时按 M1U-24 保留记录 |
| M1U-11 | 传输断开 | 立即 `kEnding`，不等待对端 `bye` |
| M1U-12 | 连续 50 次结束/重连 | 无资源增长，无残留按压 |
| M1U-13 | 旧会话 `media.answer` 到达新会话 | 静默丢弃，新会话状态不变 |
| M1U-14 | 帧槽积压（编码慢） | 采集帧被覆盖，不排队，延迟不累积 |
| M1U-15 | 控制消息 > 64 KiB | `malformed_envelope` 并关闭连接 |
| M1U-16 | 任一方身份校验失败，或会话控制、媒体、输入来自另一认证连接 | 拒绝该连接或记录，不产生媒体或注入副作用 |
| M1U-17 | 首次授权等待、本机拒绝或确认超时 | 等待期间不发 `session.accept` 或媒体，拒绝或超时释放待决槽位 |
| M1U-18 | 本机仅批准 `view` | 可看首帧，不发送 `input.prepare`，键鼠事件无普通注入平台调用 |
| M1U-19 | 配对持久化失败、取消或断线，分别覆盖取消先于最终提交许可、许可先于取消及两端提交之间中断 | 取消先到的端清除暂存，已许可且写入成功的端保留记录，迟到结果不推进已终止的协议。被控端只显示本端登记状态，控制端仅在本地激活成功时显示配对成功。再次现场确认同一身份后双方各有一条活动记录，其他信任不变，临时通道无法发起会话 |
| M1U-20 | 暂停后恢复并收到旧代次 `input.ready` 或输入 | 旧代次均被忽略，新代次握手完成后仅新输入生效 |
| M1U-21 | 本机撤权与注入许可申请交错 | 关闭后无新许可，已授权的在途调用完成并记账后清理，积压事件无副作用 |
| M1U-22 | 平台部分接受复合注入、拒绝释放事件或无法确认普通注入效果，后续输入已排队 | 按已确认效果记账并保留不确定的按压项。下一条许可之前门禁已关闭，后续事件无普通注入调用。Session 进入 `kEnding`，清理确认前不复用槽位 |
| M1U-23 | 重连时旧会话任务退出通知或渲染回调迟到 | 不推动新会话状态，旧帧不进入新会话，工作线程未重建 |
| M1U-24 | 释放被锁屏阻止或平台部分接受释放 | 只移除已确认项，门禁和会话槽位保持关闭，重试确认后才可复用 |
| M1U-25 | `session.challenge` 重复使用或换连接使用 | 拒绝请求，未启动新的本机授权 |
| M1U-26 | 认证后授予 `view` 和单项输入权限 | 只有获准类型可获得普通注入许可 |
| M1U-27 | 普通输入或信令队列已满时关断 | 关闭指令和工作退出确认仍可观察，不把旧会话提前置为可复用 |
| M1U-28 | 鼠标按住时收到当前会话的显示映射变化通知，旧坐标事件仍在队列中 | Capture 停止发布，Session 关闭门禁并进入 `kEnding`，旧坐标不再获得许可。本地清理无需坐标，清理未确认时保持 `kBusy` |
| M1U-29 | 被控端普通信令队列已满，控制端失焦发出当前代次的 `input.pause` | 暂停经独立槽按接收顺序交付，门禁封闭、队列清空并开始释放后才回 `input.suspended`。旧代次消息无副作用。有效暂停无法保留或发送时经独立关断槽结束会话 |
| M1U-30 | 阻止 Session 消费通知，将锁屏或 `kUnknown` 回调的原子封闭与 Input 许可申请做两种顺序的交错 | 封闭先发生时没有普通平台调用，许可先发生时最多完成该次调用并按实际效果清理。随后变回可交互也不得重开旧会话。旧会话通知不能封闭新会话。初始未知或订阅失败时门禁保持关闭 |

### 4.2 真机验收

使用一台 Android 10+ ARM64 真机和一台拥有本地交互式会话的 Windows 电脑。两端在同一局域网内直连。Linux 可辅助测试及采样。

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| M1H-01 | 同一对机器连续 10 次会话 | 全部成功，每次都能看到真实桌面 |
| M1H-02 | 鼠标与键盘操作 | 位置准确、按键无错乱、无残留按下 |
| M1H-03 | 分别在 Windows 本机结束会话、断开测试使用的局域网链路、锁定 Windows | 自本机得知终止事件起关闭门禁。桌面阻止释放时记录待清理，恢复后确认释放才可重连 |
| M1H-04 | 局域网延迟测量 | 每类操作从控制端输入到首次显示对应可见反馈的 P95 均 ≤ 200 ms，同时满足[架构总览 §8.3](../../architecture/overview.md#83-m1-性能预算)的帧率、首帧和覆盖率要求。P95 < 50 ms 是性能目标 |
| M1H-05 | 1 小时会话 | 无崩溃、无按键残留、关闭后资源回收 |
| M1H-06 | 远程按住鼠标按钮时改变被控端分辨率 | 旧会话结束，旧坐标不再注入，按压确认释放且资源退出后才可重新授权。新会话中的点击位置正确 |

M1H-04 保存手机型号、系统版本、解码器、刷新率、手机 Wi-Fi 至 Windows 的实际链路、RTT、带宽和原始数据路径。
在 RTT ≤ 10 ms、带宽 ≥ 10 Mbps 的链路上测 1280×720，平均解码帧率 ≥ 30 fps，首帧 ≤ 3 s，统计覆盖率 ≥ 99%，并按架构总览检查冻结和序号。文本提交、编译开始、程序启动及中断返回各采至少 20 个样本并分别计算 P95。各类验收线为 ≤ 200 ms，性能目标为 < 50 ms。现场人工确认等待时间单列。
M1H-01–M1H-03 通过也不代表 M1H-04 通过。

## 7. 线程与资源

线程划分沿用[线程模型](../../architecture/threading.md)第 1 节，Android 映射与输出所有权见 [007](../007-android-controller/spec.md#4-线程与资源)。
下表列出共用资源和 Windows 被控端的限额。帧池契约见
[屏幕帧移交](../002-screen-frame-handoff/spec.md)。

| 资源 | 所有者（线程） | 释放位置 | 上限 / 溢出策略 |
| --- | --- | --- | --- |
| 采集帧缓冲 | Capture（经 `FramePool`） | 引用归零时在持有方线程 | 池容量固定，耗尽返回空，不扩容 |
| 采集帧槽 | Capture 写入、Encode 读取 | — | 1 帧，新帧覆盖旧帧 |
| 编码输出缓冲 | Encode | Encode 线程，会话结束时 | 按 ≤ 2 帧等价字节估算，丢最旧非参考帧 |
| 发送队列 | Network | Network 线程 | 有界；溢出记数并丢弃，不阻塞 Encode |
| 输入队列 | 控制端 UI → Network，被控端 Network → Input | 各消费线程 | 每端 32 条、≤ 500 ms。超限结束会话并释放按压 |
| Android 视频输出 | Decode 拥有输出索引，UI 提供当前 Surface | Decode 释放索引和表面引用，UI 管理表面生命周期 | 各最多 1 项待提交输出、1 项首帧回执，详见 007 |
| 暂停与关断通知 | Network、平台桌面观察回调、Input、Session 按 [线程模型 §2.9](../../architecture/threading.md#29-m1-会话交接) 分工 | Session 消费 | 独立有界槽。普通信令容量不影响暂停或关断交付 |
| 统计事件队列 | Writer | Writer 线程 | 4096 条；溢出标记证据不完整 |
| 会话状态 | Session | Session 串行执行器 | 单实例，不跨线程共享可变状态 |

约束：

- 端点启动时预分配 Capture/Encode 帧池与帧槽，按 [002](../002-screen-frame-handoff/spec.md) 贯穿工作线程寿命。
  停会话时，Capture 确认不再发布后，Encode 用正常消费接口取走并释放最后一帧，释放自己持有的引用后回执。
  下一会话在回执和资源清理均确认之后启用。端点退出时才 `join` 两线程并执行 `drain_for_shutdown()`。
- 其他会话资源在启动阶段构造，停止后由各所有者线程释放。Session 通过带会话代次的退出确认判断是否
  可复用槽位，执行器自身保持可调度。详见 [架构总览 §5.3](../../architecture/overview.md#53-会话关闭顺序)。
- 热路径（Capture / Encode / Network / Input）禁止动态分配与同步文件 I/O。
- 任何新增线程或线程池都属架构变更，须先改 [线程模型](../../architecture/threading.md) 并获批。

### 7.1 风险

- 传输层自研（见 [架构总览](../../architecture/overview.md) D1）：拥塞与丢包策略在局域网外不可用，
  M1 的结论不能外推到公网。
- 控制端实际解码能力、Wi-Fi 链路和可见反馈时序按手机及系统版本记录。Windows 与 Android 分别记录各自的资源和性能数据。
- 真机延迟受显示器刷新率与测量工具影响；软件打点不能代替物理画面测量。
- Windows 显示映射变化后关闭会话。分辨率变化的关闭与重连由 M1H-06 验证，DPI 变化和显示器热插拔仍需真机验证。
