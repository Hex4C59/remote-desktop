# 任务02：地址与临时口令配对验收

2026-09-22完成。Windows C++被控端以`sender --serve`启动并显示临时口令，Android从正常应用入口输入IPv4地址与口令观看桌面。SDP与ICE均经认证TLS连接交换；USB/ADB仅用于本次自动化输入与证据回收，不参与正常信令。

设计、启动方法与限制见[临时配对协议](../design/pairing-protocol.md)。结构化结果见[配对验证摘要](evidence/task02-pairing.json)。源码沿用固定WebRTC版本，构建和设备环境与任务01相同。

## 最终验证

最终运行`a7db7cceeb5446afb04e500d453019e4`使用新启动的被控端与最终APK：

- 修改口令的证书指纹部分：TLS身份校验失败，未授权、无首帧。
- 保持证书指纹正确、修改凭据部分：收到明确拒绝结果，未授权、无首帧。被控端只在授权后创建桌面源与PeerConnection；目前没有输入注入模块，不将此项称为真实输入拒绝实验。
- 正确口令：授权、首帧、1280×720显示和DataChannel回显通过。Agent查看第一张手机截图，确认显示Windows实际编辑器桌面及“已连接”状态；第二张被手机通知面板遮挡，不作为桌面证据。此前运行`1c3bd91bc2d04d2f8314cc2aadbd13a2`的两张图也显示了真实桌面的文档切换。
- 已有会话时，第二条经过证书指纹校验的TLS连接只收到`busy`，未获得另一份offer。
- Windows日志显示媒体`peer_state=2`后仍应用了两条ICE候选；持续信令没有在首次收集完成时关闭。Android端也实际应用了逐条候选，但未人为强制其候选晚于连接建立才抵达。
- 手机切后台与TLS关闭回调均发生；未出现Java崩溃，观察窗口结束时应用进程仍存活。此项是一次实际回归，不声称穷尽所有竞争时序。
- 应用日志未包含测试的明文配对口令；Windows口令只写交互窗口，不写标准输出或文件。

最后的文件模式合成源回归`e7fbb2afa4fd42099326e8bc71766348`通过正常退出、手机首帧及消息回显。Windows和Android最终构建、Windows GN头文件依赖检查、PowerShell测试脚本语法检查、shell语法及Git空白检查均通过。Android仍沿用既有构建脚本的静态分析关闭配置，不能称为完整静态分析通过。

原始运行文件位于Windows `build/pairing-tests/<run-id>`，本地副本位于忽略的`.local/logs/`。源码仓库只保存结果摘要和截图哈希，不保存私人桌面截图、凭据或SDP。

## 修复与审查

Standards复审发现跨主线程与RTC工作线程调用结束逻辑可能重复释放native对象，已用原子状态切换保证只执行一次清理。新增切后台回归进一步复现`NetworkOnMainThreadException`，已将TLS关闭移到工作线程，保持原回归后通过。

Spec复审核对了认证、信令保护、生命周期、媒体身份绑定、持续ICE和单连接要求，未发现其他阻断问题。没有以“媒体本身加密”代替连接授权，也没有实现自行设计的密码算法。

## 限制

临时口令为64字符，认证窗口5分钟、最多10次失败，成功后仅用于该会话；不是六位PIN。断开后需重启被控端获得新口令，并从最近任务移除Android应用后重新打开。完整手动重连体验由任务05处理。

当前不支持远程输入、十分钟性能验收或公网连接。已完成的是局域网授权观看桌面；下一项任务03是触屏定位。
