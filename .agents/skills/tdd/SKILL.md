# 测试驱动开发

## 铁律

**没有先失败过的测试，不写生产代码。**

已经先写了实现才想起 TDD：删掉，从头来。不留作参考，不边写测试边迁就它，不"先看一眼再改"。

理由只有一条：没亲眼看到它失败，就不知道它测的是不是对的东西。

## 第零步：确认规格允许动手

本仓库是 SDD + TDD（[AGENTS.md §4–§5](../../../AGENTS.md)）：行为契约先在
`specs/spec-*.md` 里定稿，再进入红绿循环。

- 有对应规格且 `status: approved` → 继续。
- 规格是 `draft` → 停。功能代码一行都不写，先把规格交用户确认。
- 没有规格 → 新功能先建规格；纯缺陷修复（行为不变）可跳过规格直接复现。
- 规格要改 → 先改规格，再改代码。

完整流程与路由见 [sdd-loop](../sdd-loop/SKILL.md)。本文件只负责红绿重构这一段。

## 第一步：确定预期

写代码前列出用户动作、触发条件和可观察结果。从需求、协议或仓库约定确定预期。若缺少会改变验收结果的信息，只询问尚未确定的部分。

## 第二步：确认红灯

1. 修缺陷先复现。通过公开入口运行真实被测代码，用现有 fixture 提供外部输入（例如 `docs/protocol/vectors/`），选能覆盖行为的最快测试层级。
2. 先只改测试相关文件，再单跑目标用例。
3. 确认目标断言因当前行为不符而失败，记下命令、预期、实际和被测版本。
4. 核对失败原因：必须是"缺这个行为"，不是笔误、导入错误、fixture 缺失或环境没配好。跑不起来不算红灯，先把环境问题诊断清楚。
5. 测试意外通过时检查触发条件：可能行为已经存在，先确认是已有覆盖还是断言写错了，再决定改测试还是改预期。
6. 协议、分帧、时序等不变量补属性测试，并保存触发失败的输入。

## 第三步：让测试通过

红灯确认后直接进入实现，按需迭代最小改动。

- 已确认的测试和 fixture 视为只读；要让测试变成绿灯，只能改实现。
- 每次迭代先重跑目标用例。
- 构建与测试入口由 [AGENTS.md §2](../../../AGENTS.md) 锁定：`cmake --preset debug`、`cmake --build --preset debug -j`、`ctest --preset debug --output-on-failure`。单跑用例用 `ctest --preset debug -R <新增测试>`。不要改回其他构建系统，也不假设目标名。
- 当前仓库没有任何构建和测试入口（无 `CMakeLists.txt`、无 `CMakePresets.json`、无 `tests/`）。首次搭建时按 [specs/spec-lan-vertical-slice.md](../../../specs/spec-lan-vertical-slice.md) 第 5 节第 1 步建立 Presets 与 CTest 接线，测试框架用 GoogleTest/GoogleMock；引入框架属新增依赖，先按 AGENTS.md §3 取得批准。
- 构建入口未建立前，测试跑不起来属于环境缺失，不算红灯；先把入口建好再复现失败。
- 涉及协议或分帧时，除目标用例外还要跑属性测试；协议用例以 `docs/protocol/vectors/envelope.json` 为数据源，不在测试里另抄一份。
- 目标用例绿了不等于套件绿：完成前跑一遍完整测试命令。任何失败——包括不是这次改动引起的——都要如实报告，不能略过。
- 如果发现验收依据有误，先明确正确的预期，再从红灯重走一遍。
- 需要提交时按 [git-commit](../git-commit/SKILL.md) 处理。

## 第四步：交付证据

把红灯和绿灯的运行输出保存在 `test-results/`（不提交 Git，见 `.gitignore`），交付时列出用例、命令、结果、被测版本和证据路径。

默认在工作区完成两阶段。按用户指示暂停评审或提交；若用户要求分开提交，分别在确认红灯和完成绿灯时提交本次测试及实现。

## 常见借口

| 说法 | 实际情况 |
| --- | --- |
| "这段太简单，不用测" | 简单代码照样会坏，写个测试只要几十秒。 |
| "事后补测试效果一样" | 事后写的测试一写就过，证明不了任何事。断言按你记得的情况写，漏掉的是你没想到的分支。 |
| "我已经手动点过了" | 手动验证没有记录、不能重跑，改一次就得重来。"当时好使"不等于覆盖了边界。 |
| "写了几小时，删掉太浪费" | 那几小时已经花掉了。真正的选择是"重写一遍有把握"还是"留着自己都不敢信的代码"。 |
| "先留着当参考，写测试时对照" | 一对照就会迁就它，实质仍是先实现后补测试。删就是删。 |
| "我得先探索一下" | 探索可以，探索完丢掉，从测试开始。 |
| "测试写不出来，说明设计不清" | 对，这是信号：难测即难用，先改接口。 |
| "TDD 太慢" | 省下的是调试和回归的时间；跳过测试只是把成本推迟到联调和现场验证。 |
| "这次情况特殊" | 是否跳过验证由用户决定，不由实现者自行判定。 |

## 红旗

出现以下任一情况：停下，说明怎么退回红灯，再重来。

- 先有实现，后有测试
- 测试第一次跑就通过，且说不清它为什么本该失败
- 说不清失败原因，或失败原因是笔误、导入错误、fixture 缺失
- 为了让测试通过而改断言
- 红灯只有"跑不起来"，没有失败输出
- "先把功能写完，最后统一补测试"
- 用 mock 调用次数代替真实行为，测完仍不知道代码对不对
- 只跑了自己新加的用例就宣布完成

## 完成前自检

- [ ] 每个新增或变更的行为都有对应用例，且用例先红过
- [ ] 每次红灯的失败原因都是缺功能，不是环境问题
- [ ] 实现只写到让测试通过，没有顺手加需求外的能力
- [ ] 动工前规格已存在且为 `approved`（或属纯缺陷修复）
- [ ] 目标用例和完整套件都绿
- [ ] 红灯、绿灯输出都落在 `test-results/`
- [ ] 协议、分帧、时序的不变量有属性测试和失败输入

有一条打不上勾，就说明这次没按 TDD 走，退回红灯重来。
