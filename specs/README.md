# 规格目录（SDD 事实来源）

本目录是 [AGENTS.md §4](../AGENTS.md) 所说“没有获批的规格，不写功能性代码”的落地位置。
规格与代码同版本管理：改行为先改规格，改规格先改 `status`。

## 命名

| 形式 | 用途 | 例 |
| --- | --- | --- |
| `spec-<feature>.md` | 单个可交付行为 | `spec-screen-frame-handoff.md` |
| `spec-<feature>-<aspect>.md` | 同一功能拆出的独立方面 | `spec-input-queue-pressure.md` |

`<feature>` 用小写连字符英文，与代码目录或类型名对应，便于互相查找。
中文说明写在文档内，不写进文件名。

## 审批状态

每份规格**第 3 行**必须是机器可读的状态行，格式固定：

```markdown
status: draft
```

| 状态 | 含义 | 允许的行为 |
| --- | --- | --- |
| `draft` | 正在写，契约未定 | 可以讨论、可以改；**不得写功能性代码** |
| `approved` | 契约已定，可作为实现依据 | 可以进入 TDD 红灯阶段 |
| `implemented` | 实现与测试均已通过，契约仍有效 | 修改行为须先退回 `approved` 或改本文件 |
| `superseded` | 已被另一份规格取代 | 必须在文档内写明取代它的文件 |

规则：

- 只有 `approved` 及之后的状态才允许写功能代码。`draft` 状态下写实现视为违规，须回退。
- 状态变更在同一行完成，并在该行下一行写明批准人与日期，例如
  `status: approved` / `approved-by: user, 2026-11-19`。
- 状态只由用户批准或明确指示变更，实施者不得自行把 `draft` 改成 `approved`。
- `implemented` 不等于“完成”：验收场景必须都能指向实际运行的测试或实测记录，
  没有证据的规格保持 `approved`。

## 模板

新规格复制下面结构。每节都是必需的；某一节确实不适用时写“不适用”并说明原因，
不要删掉标题——缺失的章节和“忘了写”无法区分。

```markdown
# spec-<feature>：<一句话说明>

status: draft
approved-by: （批准后填）

## 1. 范围

做什么，不做什么。不做的部分如果属于其他规格，给出文件名。

## 2. 接口契约

类型、函数签名、错误码、线程归属。用代码块给出真实声明，
与 `include/` 或 `docs/` 中的定义保持逐字一致。

## 3. 不变量

实现不得违反的性质。每条都要能被测试断言，不用“应当”“尽量”这类词。

## 4. 线程与资源

在哪个线程执行、谁拥有内存与句柄、在哪个线程释放、队列上限与溢出策略。
与 [docs/threading.md](../docs/threading.md) 冲突时以该文档为准，并回改本规格。

## 5. 验收场景

每条给编号、场景、预期结果。可自动化的必须能落到具体测试；
需要真机的单独成节并写明运行条件。

## 6. 依赖与待决项

需要新增的第三方依赖（按 AGENTS.md §3 审批）、尚未确定的决策、
以及哪些问题一旦确定就要回改本文件。

## 7. 并发自检（仅涉及多线程的规格需要）

逐条回答 [docs/threading.md](../docs/threading.md) 第 5 节的 T-01~T-09。
不适用的条目写“不适用”，不要省略。
```

## 自动校验

[tools/check_specs.py](../tools/check_specs.py) 把本文件的约定变成可执行检查：
状态行、必需章节、编号用例、索引一致性。它作为 `spec.structure` 用例接入 CTest，
因此 `ctest --preset debug` 会一并校验规格结构。手动运行：

```bash
python tools/check_specs.py
```

校验器只检查结构，不检查内容质量；质量仍由评审负责。

## 与文档的关系

- `specs/` 是**行为契约**的事实来源：某个函数失败返回什么、队列满了丢哪一帧。
- `docs/` 是**架构与实现约定**的事实来源：分层、线程模型、协议格式、平台接口。
- 两者冲突时：行为细节以 `specs/` 为准，结构与线程以 `docs/` 为准，
  并把另一处改齐。改动任一处都要检查另一处是否失效。
