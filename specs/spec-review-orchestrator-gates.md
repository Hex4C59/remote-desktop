# spec-review-orchestrator-gates：Pi 交付流程的阶段准入与审查输入校验

status: draft

## 1. 范围

约束 `.pi/extensions/review.ts` 所注册的正常交付入口与独立审查入口。编排器实现位于 `.pi/orchestrator/`，沿用现有 L0 到 L3 审查策略及其风险分级。

## 2. 接口契约

命令在 Pi 扩展命令处理器中执行。准入失败通过当前命令的错误反馈报告，附当前阶段、缺失前置条件和可用的下一条命令。

| 命令 | 准入条件与结果 |
| --- | --- |
| `/orch start discussion [路径]` | 无活动运行或上一运行已终止时创建交付运行。处于 `DISCUSSION` 时复用该运行。 |
| `/orch start spec [路径]` | 仅在当前运行的 `SPEC_DRAFT` 时执行。 |
| `/orch start plan [路径]` | 仅在同一运行因规格获批进入 `PLAN_DRAFT` 后执行。 |
| `/orch start task [路径]` | 仅在同一运行因计划获批进入 `TASK_LOOP` 后执行。 |
| `/review` | 仅在同一运行的任务通过并进入 `CODE_LOOP` 后执行。 |
| `/review --standalone` | 运行独立代码审查。使用独立证据目录，不推进活动交付运行。 |
| `/orch resume [run-id]` | 恢复磁盘中的状态，重新应用对应阶段的准入条件。 |
| `/orch approve` | 只有待批审查包与当前审查输入仍匹配时，才记录批准并推进状态。发现变更时保留待批状态和原证据，提示重新生成审查包。 |

## 3. 不变量

- 正常交付入口依据同一运行内的状态及已记录事件准入。缺少前序凭据或状态无法读取时，拒绝执行且不改写已有运行。
- L3 验证包清单、记录的包哈希和审查输入。交付物阶段对比送审文档快照和当前输入。代码阶段对比送审的暂存区、工作区及未跟踪文件差异和当前差异。
- 规格仍由用户批准状态。L3 决定绑定已审查的规格内容，仓库规格状态行由用户批准后按 `specs/README.md` 管理。

## 4. 线程与资源

准入检查在 Pi 主扩展的命令处理器中进行。Git 命令沿用现有超时，证据使用独立运行目录和原子写入。此流程不涉及远程桌面的实时线程。

## 5. 验收场景

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| ORCH-01 | 在规格等待批准时执行 `start plan` | 拒绝，规格与现有状态保持原样。 |
| ORCH-02 | 在计划等待批准时执行 `start task` | 拒绝，计划与现有状态保持原样。 |
| ORCH-03 | 在任务通过前运行 `/review` | 拒绝，不启动构建或审查。 |
| ORCH-04 | 在前序通过后按阶段运行并中途恢复 | 每个阶段只在准入条件满足时前进，恢复后保持原运行及进度。 |
| ORCH-05 | 在交付运行中调用独立代码审查 | 独立审查产出自己的证据，交付运行的状态、检查点与审批记录保持原样。 |
| ORCH-06 | 等待批准期间修改送审文档或 Git 差异 | 批准被拒绝，已有审查包仍可供核对。 |

## 6. 依赖与待决项

复用现有 Git、Node.js 与 Pi SDK。草案采用显式 `/review --standalone` 保留快速审查入口，待用户确认后实施。
